# AVC native VCS — authoritative v0 architecture and format contract

**Decision:** 2026-10-15; **reviewed:** 2026-10-28. **Status:** selected v0 architecture under independent contract qualification; not implemented, proven optimal, or released as a stable byte format.
This document is the single authority for v0 logical source, immutable objects, revision semantics, workspace/recovery state, merge behavior, persistence and native exchange. Hosted publication is a future protocol, not part of the initial local object core. [User workflows](ux.md) own interaction defaults and qualification cases; their everyday navigation and presentation are proposals, not a validated consequence of the selected source architecture. [Research](research.md) records reasons and rejected options; [qualification](roadmap.md) records tests and release gates.

**Change and freeze policy:** The product invariants below are requirements; the selected algorithms and byte format are candidates to qualify against them. Correct demonstrated failures and compare consequential alternatives before committing user data to a stable format. Neither novelty nor incumbent adoption is evidence of superiority. Keep one current contract, update its rationale and fixtures explicitly when it changes, and never silently change IDs for released repositories. Before the first durable native repository, require independent codec/semantic checks and representative layout/merge cost evidence; full production performance qualification follows later.

## 1. Purpose, non-goals, and invariants

AVC is a native, general-purpose, local-first source VCS for ordinary editors and terminals, laptops/desktops, offline development, persistent VPS/SSH workspaces, remote/cloud environments, ephemeral agent containers and microVMs, CI/build workers, and scalable source-query services.

Source history, mutable workspace bytes, private recovery, authored revisions, shared publication, build/test evidence, and runtime/deployment images have **different owners and lifetimes**.

The mandatory user-visible invariants are:

- **I1 Exact state:** Each admitted immutable StateId reconstructs exactly one tracked, typed logical source namespace, independent of ancestry, author, cache, physical packing and editing history.
- **I2 One source authority:** Source bytes are identified by immutable Merkle objects. Changeset/patch records, diff indexes, copy hints and provenance are not competing authorities.
- **I3 Honest durable acknowledgement:** Acknowledging a State, Revision, Capture or remote draft root means all canonical object dependencies and necessary root/pins are durable within its stated failure and retention domain.
- **I4 Independent work:** Unrelated workspaces and private captures may advance without changing a global repository head or blocking another workspace's logical selection. Publication to the same target is conditional and ordered.
- **I5 No false filesystem ownership:** A normal filesystem directory is writable by external processes. Status, capture and in-place restore never claim an atomic instant or absence of races without a real controlled-writer boundary.
- **I6 Lossless uncertainty:** Every admitted ambiguous merged State preserves original source alternatives as typed conflicts; if limits prevent representing that State, refuse admission and retain protected input roots under an explicit pending receipt. A clean merge is not proof of semantic correctness.
- **I7 Offline source custody:** A full native repository can inspect/edit/backup without Git, daemon or network. An independent native export/backup can reconstruct retained source without hosted service.
- **I8 Sparse accuracy:** A missing promised object is never interpreted as absent source. A thin client with insufficient proof may stage edits but cannot assert a complete new StateId.
- **I9 No implicit execution:** Parsing or materializing untrusted source never runs hooks, downloaded code, merge drivers, agent tools or scripts without explicit authorization.

No requirement for Git object/pack/ref/protocol or interoperability, causal patch algebra, hosted forge, agent orchestrator, virtual filesystem, process snapshots, build engine or deployment controller. Git conversion belongs in a separate boundary adapter, not a native Git-compatible storage mode. Conversion must preserve the declared representable subset and report unsupported or lossy cases before writing output; it must not constrain native IDs, conflict semantics or durability. The adapter is deferred, not part of the native engine qualification.

## 2. Chosen data model and object graph

The immutable data graph has typed objects; mutable names and pointers live in a separate transactional authority.

    BlobId       -> exact byte sequence
    MapId        -> deterministic directory map of name -> Entry
    ConflictId   -> unresolved source alternatives, possibly at a subtree
    StateId      -> RootEntry (Directory, or unresolved directory Conflict)
    RevisionId   -> StateId, ordered parents, ChangeId, authored metadata,
                    optional immutable provenance reference
    ProvenanceId -> owned result StateId; non-owning typed input IDs,
                    conflict/operation claims; no output RevisionId

    Entry = File { blob: BlobId, executable: bool }
          | Symlink { target: BlobId }
          | Directory { children: MapId }
          | Conflict { value: ConflictId }

    RootEntry = Directory | CoupledSubtree Conflict of present directory alternatives
    ChangeId  = 128-bit cryptographically random logical authored identity

**State identity versus history identity.** A StateId describes the source value alone, including typed unresolved expressions. Two different authors or histories can create the same StateId. RevisionId includes that StateId, ordered parent RevisionIds, ChangeId and immutable author/description/time/provenance. Two Revisions can have equal State and different IDs. ChangeId normally persists across amend/rebase and does **not** imply a context-free patch, one-time application, or immunity to diverging rewrites.

**Revision DAG:** zero parents is a root; one parent is normal; 2–64 ordered parents is an authored merge. Parent IDs must be distinct; order is preserved for first-parent history/provenance, **not** source reconstruction. Every Revision directly names its full StateId; zero-parent roots are separately valid source states. The canonical object-reference graph (including parents and provenance) must be acyclic and checked upon admission (a hash match is not a substitute for graph validation). No unknown, missing or promised parent is treated as empty ancestry. Evolution edges are metadata, not Revision parent edges.

**Evolution:** Rebase/amend/split/fold produce new RevisionIds and optional evolution records relating predecessor/successor revisions. These are local authority metadata, append-only while retained and exported with the retained metadata snapshot, not canonical Revision references or merge ancestry. Validate the separate directed predecessor-to-successor graph transactionally: no self-edge or cycle, and a no-op replacement needs no edge. Do not combine those edges with the reverse references in canonical provenance to invent an object cycle. Old revisions remain intact while roots, recovery policies or explicit pins protect them; an evolution record alone does not extend retention. Its IDs/relationship may outlive endpoint bytes, in which case queries report an expired/unavailable endpoint rather than claiming reconstructability. A newly authored independent change receives a new random ChangeId; rebase/amend retains its old ChangeId; split/fold records explicit many-to-many lineage with newly assigned ChangeIds rather than deriving identity from timestamps.

**Provenance and custody:** A Revision owns its Provenance object, which owns only its bound result State. Other typed input IDs, expected values and evidence IDs are **non-owning commitments**, not ancestry, availability promises or permission to fetch. A cleaned-up amendment must not retain/export a discarded private predecessor merely through audit metadata. The containing ProvenanceId and output RevisionId cannot be audit inputs. Actual parent history remains owning. Authorship/provenance never enters StateId.

## 3. Canonical v0 object encoding and IDs

**Chosen hash:** 32-byte BLAKE3 digest, object-kind separated. Canonical payloads use a single deterministic binary codec, not Rust struct layouts, JSON, CBOR implementation defaults, filesystems, SQLite page bytes, or physical compressed streams.

For every kind:

    ObjectID(kind, payload) =
      BLAKE3-256(
        bytes("AVC-OBJECT\0v1\0")
        || u8(kind)
        || u64le(payload_length)
        || payload_bytes
      )

The complete ObjectID is the **pair (kind, 32-byte digest)**. Its canonical external spelling is `avc1-b3-kXX-<digest>`, where `XX` is the two lowercase hexadecimal digits of the actual u8 kind and `<digest>` is exactly 52 lowercase RFC 4648 base32 characters without padding (unused final pad bits must be zero). Short forms are only UI abbreviations. All wire references carry actual kind plus full digest; a digest alone is not a typed ObjectID. Every retrieval verifies the envelope hash, expected reference kind, canonical decoding and referenced closure. Re-encoding a decoded object must reproduce the exact payload bytes.

Primitive grammar:

- **u8, u16le, u32le, u64le, i64le:** fixed-width, little-endian. bool is exactly 0 or 1; no floats. A path name is a length-prefixed raw byte string; all byte strings have explicit lengths.
- **byte-string:** u32le length followed by bytes, unless a particular field uses u64le for large file content. No Unicode normalization; invalid UTF-8 is valid content/name subject to pathname rules.
- **optional:** u8 presence flag 0/1, followed by its field if present. Arrays: u32le count then contiguous canonical elements; reject unknown tag, trailing bytes, duplicate entries and noncanonical ordering.
- **object ref:** u8 expected kind followed by 32 digest bytes. An owning ref requires complete canonical dependency closure. A non-owning typed **ID commitment** uses the same bytes but is not a graph edge; its schema explicitly marks that distinction. Decoding a commitment never fetches/requires its object. A mismatched kind is a structural error. Maximum nesting/depth and total expansion are enforced independently of encoded lengths.
- **Blob (kind 1):** payload is exactly raw file/symlink byte content (u64le length lives in the common envelope); a huge blob is streamed and never needs to fit memory. Content chunking/compression are *physical* only.
- **MapLeaf (kind 2), MapBranch (kind 3):** specified in section 4; both are MapId family, with their actual typed kind encoded in references.
- **State (kind 4):** one RootEntry descriptor, no author, history, timestamp or path-index cache.
- **Revision (kind 5):** typed ref(State); u32le parent count and ordered typed ref(Revision) parents; 16-byte ChangeId; author as byte-string; description as byte-string; i64le authored Unix nanoseconds; optional typed ref(Provenance). UTF-8 may be required by a UI but canonical bytes are retained. Signatures and mutable review notes are separate immutable attestations referencing RevisionId.
- **ConflictValue (kind 6):** specified in section 6; it identifies source alternatives, not authorship/merge engine.
- **Provenance (kind 7):** owned bound result State and non-owning input/conflict/operation commitments in closed typed Transform/Merge/Observation records; section 12 fixes its fields. It describes source construction, never replaces State authority or authorizes execution by being decoded.
- **Retired experimental tags 8 and 9:** reserved and rejected by the local v0 core; the earlier ConflictGroup and PublicationCandidate schemas are not supported. Never reuse these tags.
- **Other immutable protocol, evidence and backup records:** distinct future kind tags and versioned schemas; never reuse historical tags.

The object envelope is the *hash input*, not a claim that physical storage writes one file per payload. A MapId reference carries the **actual** MapLeaf or MapBranch kind tag; either is valid only in a map-reference slot. A State root carries an Entry descriptor constrained to Directory or a Conflict whose alternatives are directories. A decoder must reject pathological allocations before allocating by an untrusted length. Different object-kind registries and future codec revisions require **new IDs**; old decoders and explicit ID mappings remain supported for histories that have been published. Hash IDs verify integrity, **not authenticity, authorization, secret protection or object availability**.

## 4. Source namespace and deterministic Merkle map

Canonical file types for v0: regular file with exact Blob bytes and executable bool; symbolic link with exact target bytes; directory, including empty; and a typed unresolved conflict. Do not canonicalize mtime, owner, OS-specific ACL/xattr, hard-link identity, device nodes, generated file contents or line endings. Unsupported admission is an explicit error, not lossy conversion.

Path components: nonempty, raw byte names, no NUL or slash, not "." or "..". v0 upper bound **255 bytes per component**, **4096 path bytes** including separators, **256 components**. A directory cannot also be a file/symlink. Reject duplicate child names. Case/Unicode normalization is **not** part of source equality; materialization on a filesystem unable to represent names must fail safely and preserve original source. Symlink target content is data; never follow an untrusted link when materializing the tree or checking containment.

**Choose a hierarchical Merkle directory tree whose each child map is one deterministic path-compressed radix map over byte-name nibbles.** The map is independent of insertion order. The particular algorithm is fixed for v0:

1. Encode each child name as a sequence of high/low four-bit nibbles. The entry descriptor is one tag plus its BlobId/MapId/ConflictId and optional executable flag. At a map trie position, keys are remaining nibble suffixes.
2. **Leaf:** if the canonical leaf representation of all remaining entries at this position fits **4096 bytes**, encode exactly one sorted leaf. Leaf payload is u32le entry count followed by records sorted lexicographically by full recovered byte name: u16le suffix nibble count, packed high-nibble-first suffix bytes (zero unused low nibble), then canonical Entry descriptor. Empty map is one empty leaf. No leaf may exceed 4096 encoded bytes.
3. **Branch:** otherwise take the **longest common remaining nibble prefix**, encode it once, then create a terminal Entry if a name ends there and child MapIds for nonempty next-nibble groups. Payload is: u16le prefix nibble count, packed prefix, u8 terminal-present, Entry only when flag=1, u16le bitmap, then child kind+hash in ascending nibble order. The branch consumes that prefix plus one nibble on each child edge. At least two terminal/child outcomes are required; one-child chains are path-compressed. Child groups recursively apply the same leaf/branch rule.
4. **Canonical normalization:** if a branch's entire key/value set would fit in a leaf, it must be a leaf. A branch's prefix must be maximal. Empty children, uncompressed one-child chains, overlapping ranges, duplicate keys, bad nibble padding, or inconsistent subtree membership are rejected. This makes identical maps yield identical encodings **regardless of editing/update order**. An update at a threshold may rewrite the affected local subtree but not unrelated sibling directories.
5. Directory entries reference a child map; relocation/reuse of an unchanged directory subtree changes only its ancestor links. A map is immutable; range scan/lookup/diff use nibble order and Merkle subtree equality. Sparse membership and absence witnesses must include the full trusted ancestor path and any relevant leaf/branch boundary proof, not just an unverified "not found" response.

**Name encoding example:** both names "a" and "ab" can coexist. An ending name is a terminal at its path; it must never be confused with a longer name sharing its prefix. Odd-length nibble prefixes carry a zero unused padding nibble and must be validated. Separate directory levels prevent confusing a filename containing slash with nested paths.

**Normative construction/check:** For one child-directory map, take its unique sorted (raw byte name, typed Entry) pairs. `Build(S)` emits a MapLeaf **iff** `4 + sum(2 + ceil(remaining_nibbles/2) + encoded_Entry_size) <= 4096`. Otherwise emit a MapBranch at the **exact** longest common nibble prefix of all names in `S`, with a terminal only if a name ends there; partition the remaining names by the next nibble, recurse with that edge consumed. For a singleton key the leaf bound always holds under v0 name/Entry sizes. Empty MapLeaf payload is exactly `00000000` in hex (u32le count zero; **four zero bytes**), and its kind tag is 2 in the enclosing hash framing; no empty branches. This definition is a function of `S`, not of insertion sequence, cached page boundaries, or edit order. A full verifier reconstructs sorted names in the **parent's nibble context**, checks complete byte names, prefix maximality, leaf-threshold inequality, bitmap/terminal cardinality, no duplicate/range overlap and child canonicality, and requires reconstruction to re-encode to identical objects. A leaf stored below an odd-depth nibble edge may have odd-length *remaining* suffixes; an ending **complete name** or terminal may not end halfway through a byte. Bare child MapIds describe suffix maps, not absolute paths: validity must be checked from a directory-map root with accumulated prefix parity and path bounds. A thin reader cannot certify an unavailable subtree merely from an outer digest; complete validation belongs to a holder of the required closure.

Why not a flat single directory blob? Wide directories would rewrite it on every small edit. Why not canonically require a content-defined POS/prolly B-tree? Ordered scans and page packing can be excellent, but source path-prefix lookup, subtree moves, and deterministic upper fanout support this radix choice with fewer boundary-shift dependencies. **Physical** cache pages/batches and optional query indexes remain free to use different layouts without changing StateIds.

The [bounded layout study](research.md#11-from-scratch-simplification-review--october-27-2026) compares flat, packed and one-key-leaf maps. It supports retaining this packed candidate, not a universal speed claim: smaller update payloads in an unpacked trie can cost substantially more objects and total bytes. The **4096-byte leaf target**, nibble branching and codec above are v0 format choices. They are not performance facts and must pass actual golden vectors, adversarial-wide-map and byte-size checks before the format becomes usable. After release, tuning physical packing must not silently change canonical hashes.

## 5. Constructing and observing source

Source construction is a pure conditional transform against an immutable base StateId:

    Apply(base_state, requested_edits, expected_path_witnesses)
      -> either CompleteStateId or typed Conflict/Error

Edits: Put(path, expected_previous_or_absent, new Entry), Remove(path, expected), CopySubtree(source typed immutable subtree value, destination, expected_destination), and MoveSubtree(source path, destination, expected_source, expected_destination). The source of a Copy is a content-addressed immutable value, **not a reference to an otherwise-dead historical revision**. A move is the corresponding source binding removal and destination insertion with value reuse, checked atomically.

Structural-phase expected path/absence conditions refer to the pinned **base**; ordered leaf-phase witnesses refer to the computed post-structural view. Structural operations are resolved from that base as one batch: verify all source and destination witnesses, acquire protection for every reused subtree, remove all move sources, then install nonoverlapping copied/moved destinations atomically in the new immutable value. A destination's existing value cannot be overwritten without an explicit exact expected value and policy. Reject source/destination aliasing, move into its own descendant, conflicting paths, ambiguous chains/swaps and structural cycles; there is no unspecified order among requested structural operations. A separately ordered leaf-edit phase may explicitly target post-structural names with exact witnesses from that computed view (e.g. move src/ → lib/ then edit lib/x). Before building the destination root, prove **all descendants** of moved/copied subtrees still satisfy max 256 components/4096 path bytes after relocation; a trusted cached subtree depth/maximum-relative-path summary may supply this proof only if previously **computed by complete traversal and validation** of the exact typed subtree hash and codec version; otherwise independently traverse the subtree. Imported unverified summaries have no authority. A Directory-valued Put can relocate descendants too: validate each ordered post-edit view before another edit can conceal an overflow or resource failure. A valid final State does not excuse an invalid intermediate. No claim that a subtree move is O(1) when an uncached bound check must expand it. Reject the whole transform on any failed condition; no partial StateId is admitted.

The API can preserve a **recorded user-commanded Move** with explicit source/destination identity and conditions. A filesystem observer sees deletions/creations; even a unique exact byte match proves content equivalence, **not rename intent**. Inferred matches and similarity are advisory hints and may guide a user-confirmed merge recipe, never silently decide a contested delete-vs-move or edit-vs-move. A directory move is cheap when the immutable subtree is known; an unrecorded move-and-edit may require more changed paths or a conservative conflict.

**Normal filesystem capture:** tracked/admitted files are enumerated and hashed; old immutable base provides unchanged path values. Watchers, stat checks, double scans and mtime caches are hints. Without exclusive writers or a real filesystem snapshot, even two successful scans do not prove that all captured files coexisted at one point in time. The State identifies exactly the bytes AVC admitted; its authored Revision must carry observation scope/consistency provenance instead of claiming a live-directory instant. A user-selectable partial-path author operation uses unchanged base for unspecified paths and never silently includes secrets or ignored/untracked files.

**Partial client:** a trusted service verifies the complete exact base State, all affected membership/absence conditions and rebuilt root closure, or a client holding all sibling commitments and verifiable witnesses recomputes that root locally. A proof is anchored to an authenticated *authorized* StateId, not merely a claimant-supplied digest; proof availability is distinct from permission to disclose it. Ordinary raw Merkle leaf/branch witnesses reveal neighboring names, Entry types and hashes. **Path-restricted principals are therefore not given raw ancestor proofs** unless the whole disclosed node set is authorized; their edits must be verified and rooted server-side and returned as a signed/authorized scoped result. If a disconnected client lacks sufficient authorized closure, it may durably queue a pending conditional edit bundle, **not** claim a complete validated StateId. A full local clone remains self-contained and offline.

## 6. Merge and conflict semantics

**Default:** conservative three-way source-state merge; deterministic for fixed input source values, recorded structural hints and driver version, but not associative or a proof of program correctness. The exact algorithm, content-derived work budgets and ambiguity policy are part of a merge *recipe*, not of the content-object decoder. Transient execution failure (allocation failure, deadline, cancellation, unavailable object, I/O failure) returns a typed aborted/pending outcome with **no output StateId**, never a fabricated source conflict. Preserve promised input protection and allow a retry; only explicit versioned, content-derived checks may select a conflict result. The basic value rules are:

    if L == R:                          return L
    if L == B:                          return R
    if R == B:                          return L
    if B,L,R are all directories:       merge each child with its B/L/R values
    if B is known absent and L,R directories:
                                        merge independent child additions
    if B,L,R are suitable text files:   bounded conservative line merge
    else:                               unresolved typed conflict

Directory recursion with B absent treats each child as absent; equal additions coalesce and unlike same-name additions conflict. If B was a file/symlink/conflict or an indeterminate type, two *different* new directories do **not** silently union. If a parent is deleted on one side and modified on the other, form a conflict over the whole affected subtree, never discard the modification. File mode, type, symlink and binary changes follow equality/base rules only in the default driver.

**Candidate text driver `avc.text.lines/v1`:** After equality/base rules, consider only three regular files with equal executable mode, valid UTF-8 **without NUL**, each at most 1 MiB. Tokenize as exact byte lines, retaining LF/CRLF/CR terminators; no synthetic empty line after a trailing terminator. An alignment is a chain of byte-equal `(base_index, side_index)` matches with both indices strictly increasing. Compute exact maximum-length chains. A unique optimum on each side takes the sparse fast path. Ambiguity is **not automatically a conflict**: automatic combination is allowed only when **every pair of optimal alignments merges cleanly to the same exact bytes**. Any conflicting pair or different output remains a path conflict; never pick a convenient alignment or trim prefixes/suffixes to force uniqueness.

For each base-to-side comparison, first compute `r = sum(freq_base(line) * freq_side(line))` without enumerating pairs. A path conflict results if `r > 4,000,000` or `r * ceil(log2(side_line_count + 1)) > 64,000,000`; these are deterministic candidate driver budgets, not timing/performance claims. Otherwise compute sparse suffix ranks: a match `(p,q)` has rank `1 + LCS(base[p+1:], side[q+1:])`. Process base rows descending and side positions ascending, querying only strictly greater side positions. Immediate updates from the same base row cannot enter those queries. Aggregate disjoint side ranges by longest length and sum of distinct maximum chains **starting at a pair**, with counts saturated at 65. The empty alignment is exactly one chain. Decide the 64-alignment limit only after all rows: an intermediate ambiguous maximum can be superseded by a longer unique optimum. Reconstruct a unique optimum by a monotone row scan, without the ambiguous enumeration budget. The reference stores packed ranks and row/side positions, not per-match Python traceback nodes or a dense suffix table.

For an ambiguous comparison within that limit, enumerate **all** optimal pair sequences by their next matched pair, not duplicate traceback paths through skipped cells. A prefix state `(i,j,t)` needs `t` further matches. Scan candidate base indices `p` from `i` through `base_line_count-t`, counting each row once even if no match exists. For each row, examine byte-equal side indices `q` from `j` through `side_line_count-t`, counting every such pair before testing whether its sparse rank equals `t`; only those satisfying it extend the prefix. A zero-length suffix completes the sequence without a search. Limit each side to 4,000,000 of these row-plus-pair work units. Share the current path during enumeration rather than copying its full prefix at every step. Limit the left/right cross-product to 256 and `pair_count * (base_bytes + left_bytes + right_bytes)` to 32 MiB; check cardinality/byte limits before expanding alternatives. Retain hunk alternatives rather than every full anchor list. The former 1,000,000-cell gate is retired because no dense matrix is allocated; the sparse, variant, enumeration and combination limits are unchanged. Exceeding any content-derived budget yields a path conflict; allocation failure, cancellation and other transient failures still yield **no admitted State**. Budgets are symmetric in left/right; no wall-clock cutoff changes source output.

For each alignment pair, derive half-open replacement intervals and zero-width insertion gaps. Combine disjoint replacements and insertions at distinct gaps **outside the closed boundaries** of another side's replacement; identical hunks coalesce once. Thus a replacement `[3,5)` conflicts with another side's insertion at gap 3 **or 5**, intentionally conservatively. Different insertions at one gap and any other overlap become a path conflict. Scan sorted hunk lists rather than comparing every pair. Emit exact unchanged base spans and side bytes in base order, without terminator normalization. Accept only the common byte result across every alignment pair.

The [text reference](experiments/text_merge_reference.py) checks alignment sets against 961 exhaustive small pairs, confluence against 3,375 independent small three-way cases, 2001-line unique/ambiguous files, capped partial counts, boundaries and CRLF. The [controlled source study](experiments/text_merge_study.py) reproduces harmless blank-line ambiguity; the [same-cohort sparse refinement](research.md#21-sparse-ambiguity-without-a-dense-fallback--october-29-2026) preserves the public-history sample's prior clean outputs while reducing additional refusals and one measured allocation peak. Neither establishes general workflow cost. These are explicit revisions to the **unreleased** `avc.text.lines/v1` draft before freeze, without changing object framing. Retiring the matrix gate changes some former budget-conflict results: old draft recipes claiming those conflicts need not replay under this revision. No stable native repository compatibility is claimed. Refusal/re-review burden, remaining budgets and broader workload/native resource qualification remain open. After release a rule/budget change needs a new driver version, not a new object decoder.

**Recorded-Move merge rule:** Use an explicit side's Move(s→d) as a path mapping only if the original base `s` has the exact old Entry, the mapping is one-to-one and prefix-injective, the side's resulting destination is exactly the moved subtree **modulo separately recorded checked edits**, and the other side retains that source's Entry kind, has traversable directory parents, and leaves `d` **exactly equal to its base value**. A nonempty base destination may be replaced only under the Move's checked exact overwrite witness; its unchanged presence is not a concurrent occupation. A changed destination, whole-source deletion/type replacement or blocked parent cannot be transported. Transport ordinary modifications/deletions to **already existing base descendants** of `s` under `d` and apply them with the same three-way equality/text rules against the original source's base values. Edits that are new additions under an old directory name `s` remain **coupled conflicts by default**, including children introduced by replacing a leaf with a directory: intent to follow the moved directory cannot be deduced. A checked post-structural recreation of `s` on a moving side is instead a known fresh binding: keep it at `s`, never confuse it with the moved identity. A source-only merge has no move intent. A history merge must explicitly supply validated move evidence relative to its selected base and each side; it must not search arbitrary ancestry and guess which old commands still apply. The evidence binds exact base/side StateIds, ordered checked structural operations and post-structural edits, and must replay to that side's State before it can authorize remapping. A move recorded further back or on a rebased successor is usable only through a newly checked base-to-side recipe. Ephemeral virtual revisions carry no inferred move intent; any supplied evidence must be checked against their exact computed States. Two verified sides moving the same source to the same destination can merge the descendant edits and their explicitly checked fresh-name additions; different destinations, transitive/colliding mappings, new conflicting paths, delete-vs-move and ancestor/type collisions produce a conflict at the least common ancestor containing every coupled original/destination path. Do not allow a proposed mapping to overwrite another side's files, drop a deletion/edit or silently modify unaffected paths. Inferred content matches/similarity from ordinary filesystem scans are **suggestions requiring user-confirmed recipe**, never automatic evidence of identity.

The [bounded operation reference](experiments/operation_reference.py) now qualifies Source Merge with at most one Move per side: one-sided transport, matching two-sided mappings and coupled overlapping mappings. All supplied evidence is replayed **before** source equality/base shortcuts. History-with-moves, multiple Moves per side and independent different-mapping composition still refuse as unsupported, including otherwise convenient equality cases; they never silently become source-only merges. This narrows executable qualification, not canonical record acceptance. [Cases, draft clarifications and limits](research.md#23-recorded-move-source-merge-qualification--october-29-2026).

**Merge bases:** For two Revision DAG tips, compute *all* maximal common ancestors (no common ancestor is itself an ancestor of another). With one base, merge its State. With none, refuse by default; an **explicit unrelated-history merge** uses the canonical empty-directory State as synthetic base and records that choice. With several, reduce their full sorted RevisionIds by recursively forming ephemeral virtual revisions: `V1=B1`, `Vi=MergeRevision(Vi-1,Bi)` with parents `[Vi-1,Bi]` and its computed State. An ephemeral virtual node is **not authored, persisted or given a RevisionId**; it carries explicit parent ancestry and a deterministic recipe key for memoization. To merge each pair, compute its own maximal common ancestors in this augmented finite DAG (strictly earlier than both inputs), recursively reduce that frontier, then merge the two source States over the reduced base. Thus later pair merges retain the ancestry of earlier virtual nodes rather than incorrectly merging two source snapshots without a base. The Merge record binds the two input revisions, source/text algorithm versions and explicit permission for synthetic empty bases throughout this reduction. Frontier, reduction order and virtual-node inputs/results are deterministic **derived traces**, not a second persisted graph. An inspect/replay command may expose that trace; verification recomputes it. A recursive pair with no common ancestor requires the recorded unrelated-history permission; tips sharing unrelated roots do not authorize silent synthesis. Detect graph cycles, bound work/depth and return `MergeTooComplex` **without admitting a resulting State** if bounds are hit; retain/pin input States and pending operation data instead. A binary conflict cannot represent an uncomputed virtual merge. N-way proposal composition is explicitly ordered, not claimed associative or commutative.

### Conflicts are typed source values, not marker files

    ConflictValue {
      base: EntryValue,                      // MaybeEntry, absence is real
      alternatives: [EntryValue; 2],         // sorted distinct opaque values
      kind: PathValue | CoupledSubtree
    }

The canonical ConflictValue contains **only unresolved source semantics**; source EntryValue can be absent, File, Symlink, Directory or an earlier ConflictValue reference. The outer StateId includes the conflict value; equal unresolved values with the **same nested expression shape** have equal source hashes. The same flattened alternatives in different binary groupings are different values; no associativity is promised. Source conflicts can be file, path, directory, binary, delete/edit, and **coupled across multiple paths** (e.g. divergent renames).

For a multi-path coupled conflict, place an Entry::Conflict at the **lowest common ancestor subtree** containing *all affected bindings*, using complete original scope values from the selected sides/base. Enlarge that scope to a missing/opaque ancestor if it cannot otherwise be reached without traversing a non-directory. Apply whole-value equality/base reductions at that scope; otherwise retain those original values, without flattening nested conflicts or rewriting them with inferred agreement. Use CoupledSubtree when the scope values are directories/absence; a nonroot opaque or type collision is a whole PathValue instead, since File/Symlink and arbitrary opaque values cannot be placed in a strictly directory-valued CoupledSubtree. Merge normally **outside** the scope. Unrelated changes inside the necessary scope can remain coupled; automatically merging them into both alternatives would be a separate policy requiring qualification. At the State root, only **present recursively directory-valued** alternatives are legal, including within nested conflicts—a deletion hidden below another CoupledSubtree is invalid. Reads of a descendant traverse **every** alternative (including nested conflicts); if all alternatives yield the same typed Entry/absence, return it as agreed, otherwise return an unresolved **query result**, not a fabricated persistent Entry. A non-directory encountered on one branch cannot be silently interpreted as a directory with absent descendants. Missing/promised objects yield Unknown, not absence; no incomplete answer proves agreement. Materialization never silently chooses a branch. This permits agreed siblings under a high-level conflict without changing the canonical State. The historical `base` is not another live alternative for agreement. At the requested endpoint, return the exact typed Entry, including an opaque Conflict; knowing that Entry does not resolve it.

The [agreed-query reference](experiments/source_query_reference.py) qualifies this over complete protected States. It distinguishes a known Entry/proven absence, a non-directory obstruction, and an ephemeral unresolved result; equal obstructions can be reported without inventing absence. It retains the decoder's checked directory maps and conflict records, without skipping validation in another path/root context. Missing/unacquired input protection refuses before a reader exists, rather than proving an agreed answer from an incomplete branch set. This is not yet per-branch sparse Unknown/hydration, a native lease, or Blob-content streaming. Agreed reads confer no write/resolution authority: conditional transforms still refuse traversal through a conflict. [Evidence and limits](research.md#22-agreed-descendant-query-qualification--october-29-2026).

Normalization rule: equality/base simplification occurs **during a particular merge operation**; it is not a decoder license to invent missing history. Otherwise sort alternatives by canonical encoded semantic EntryValue, deduplicate exact terms, preserve the (possibly nested conflicted) base and source alternatives, and resolve to one Entry only when justified. Do **not** flatten arbitrary nested conflicts or assume identical bytes imply identical causal edits. Each pairwise producer emits at most two direct alternatives; ordered multiway composition retains nested nodes. Whole-value equality/base rules apply only to the outer inputs: an inner term matching another side is not permission to cancel or resolve it. This removes width-group machinery, but long composition chains consume the depth budget and can refuse otherwise legitimate wide merges. On nesting depth >64 or other resource budget failure, return `MergeTooComplex` without a new authored State; durably retain original input roots/pending proposal under an explicit retention receipt if requested. No acknowledged result may discard alternatives or claim to be a conflict State it cannot decode.

**ConflictOrigin/Provenance** is *separate*: input RevisionIds, relevant paths and side roles, closed operation data, algorithm versions, checked move evidence and explicit observation resolutions. Merge frontiers and virtual traces are derived from those inputs and versions. The output Revision owns a ProvenanceId; the provenance never names that output RevisionId (no reference cycle). Two revisions may contain an equal conflict source value with different causal explanations. v0 is not a causal patch algebra: deduplicating identical source terms is a **source equality choice**, not a claim of causally correct selective undo.

**Presentation:** conflict marker files are optional, generated lossily for an ordinary editor. The Materialization authority owns a manifest binding destination identity, selection/materialization generations, path, exact generated marker bytes/hash, source ConflictId and presentation codec. Persist that manifest with the protected journal **before** marker bytes can become visible. While a workspace still needs that presentation/pending record, Materialization owns its bound Conflict/alternative closure and required pending bytes independently of expiring recovery captures. Release or replace those roots only through a checked resolution or protected materialization transition, not ordinary checkpoint expiry. Unregistering must transfer still-needed records into the return descriptor. This protects interpretation inputs, not every historical working copy forever. An unchanged bound marker remains the original Conflict Entry on capture/import. Changed marker bytes are preserved as **pending resolution observations**, not admitted File replacements; promotion/import requires an explicit validated resolution. If a path crosses a source conflict but the manifest is missing, stale or incomplete, fail closed: preserve observed bytes and uncertainty without guessing that the conflict was resolved. Never infer conflict identity by parsing marker-like text in an ordinary file. Binary/directory/coupled conflicts may have no marker presentation. Resolve by choosing or constructing new Entries; prior conflicted inputs remain inspectable.

## 7. Rebase, amend, undo, revert and change identity

**Rebase** of single-parent Revision C with old parent P onto new base Q is a defined three-way source transformation:

    outcome = Merge(base=State(P), left=State(Q), right=State(C))
    C' = new Revision(state=outcome.State, parents=[Q],
                      logical_change=C.logical_change, ...)
    Evolution(C -> C', Rebase)

The result may be conflicted; old C remains immutable. An explicit selected stack is rebased in topological order, mapping already-rebased parents. Do not automatically rewrite unrelated descendants or accepted targets. Rebase of a multi-parent merge requires an explicit parent-mapping/merge recipe; v0 **rejects unsupported merge-commit rebase** rather than guessing.

**Amend** constructs a replacement Revision from an explicitly chosen new State/metadata with the **same ordered parents and ChangeId**; it does not mutate the old Revision or implicitly rewrite its descendants. A filesystem amendment uses the checked capture/observation path but is not ordinary PromoteCapture: preserve the amended revision's parents/ChangeId rather than parenting to the capture base and creating a new change. Its discarded input is private recovery/evidence unless separately included as a real parent. **Undo** conditionally restores scoped private root selections/capture/operation outcomes, with preserved receipts; it does not overwrite live filesystem bytes. Scope includes local work identity where applicable, not merely equal selected RevisionIds: another effort at the same revision cannot undo this effort's history. For single-parent revision R with parent P, **Revert(R onto Q)** is `Merge(base=State(R), left=State(Q), right=State(P))`; **Reapply(R onto Q)** is `Merge(base=State(P), left=State(Q), right=State(R))`. Both may conflict and create newly authored revisions rather than resurrecting old RevisionIds. Reverting a merge revision requires an explicit selected mainline parent, recorded with the recipe; a root revision has no implicit inverse. No everlasting "seen ChangeId" blacklist; divergent logical ChangeId successors remain distinct immutable revisions.

Content equality, revision identity, logical ChangeId, operation receipt, merge provenance and validation evidence are independent concepts; no single ID conflates them.

## 8. Workspace state, recovery and materialization

Concurrent independent writers get distinct **writable directories**; serial human tasks normally reuse one directory through preserve-and-return switching. Immutable source and authorized cache entries can be shared. Workspace ID, actor/session ID, process/VM ID, root selection and on-disk inode identity are separate. Several workspaces may select the same immutable Revision; no exclusive branch-checkout rule is required. Source-directory separation does not isolate processes, ports, databases or mutable dependencies.

Workspace source, recovery and materialization resources have **independent version/generation**:

    Selection { workspace, generation, target }
    target = Revision(RevisionId) | StateOnly(StateId)
    CaptureHead { workspace, generation, latest_CaptureId }
    Materialization {
      workspace, generation, intended_StateId, destination_identity,
      phase: Preparing | Writing | Verified | Incomplete,
      operation_receipt
    }

A new repository pins the canonical empty State as a StateOnly selection, with no synthetic authored Revision. Its first commit is explicitly zero-parent. A StateOnly recovery base with no known history requires an explicit parent/root-authoring choice; never invent ancestry from equal StateIds. All selection targets own their complete source closure.

**Administrative boundary:** Live repository/workspace control storage, SQLite DB/WAL/sidecars, staging and journals are not source-capture inputs. Identify them from trusted registration/location and file identity, not an editable ignore pattern or an untrusted source file claiming to be configuration. Default new-file discovery must not recursively ingest its own store. Explicit capture/author requests overlapping protected administration refuse rather than bypassing this boundary. Materialization must also refuse collisions with those control locations or aliases; it cannot overwrite the authority protecting its before-images. This is a destination/administration constraint, not a new global forbidden name in canonical States: retain otherwise valid source and offer a safe destination/layout instead of silently renaming it.

A status call is a **fresh observation**, not a permanently correct Clean flag. It records observed dirty/new/missing paths, scan failures and watcher uncertainty, plus the selected target/generation. Read-only status is read-only by default.

**Recovery Capture** is a *separate private authority with explicit retention*:

    Capture {
      local_work_ref, base_StateId, optional_exact_base_RevisionId,
      observed_selection_generation,
      admitted_bytes_and_deletions, pending_resolution_observations,
      recovery_scope, path_origins, covered/failed/skipped_paths,
      consistency: PerFileObserved | WriterQuiesced | FilesystemSnapshot,
      durable_receipt, created_at, retention_deadline
    }

Capture may use immutable overlays/deltas against a pinned base with bounded replay depth. It is not an authored Revision and does not trigger public share, CI, review or target movement. Only bytes actually admitted and acknowledged are protected. Capture triggers: explicit request or explicitly configured editor/agent boundary; a watcher/daemon is optional and must report missed-event gaps. A capture's original base, any recorded base Revision and all admitted/pending bytes stay pinned through its promised retention. Promotion cannot release its original receipt's protection early unless the user explicitly changes that retention obligation. If a concurrent selection change makes a capture outdated, keep its acknowledged bytes as historical recovery rather than retarget it. The capture head can fail to advance on CAS, while the separately acknowledged capture remains pinned. Distinct selection and capture generations eliminate false logical conflicts.

Recovery scope is independent of authoring selection: admitting a new file privately does not make it tracked or consent to author/share it. Path origins distinguish tracked-at-recorded-base from new/private observations; pending resolutions and coverage stay explicit. Membership in a private captured State is not workspace tracking status. These are not persisted authoring choices or a staging index: later commit selection comes from that invocation/confirmed candidate, not an old capture's inclusion or exclusion. Preserve observed origins through all checkpoint recovery, including fresh-directory recovery and a StateOnly base before first authoring; do not select the broader captured State as a new base that silently tracks private files. Exclusions, resource limits and failed observations cannot be silently counted as covered. The default inclusion policy is owned by [the UX contract](ux.md#2-selection-and-preview).

**PromoteCapture:** Author the exact capture value against its recorded base, not the directory's current bytes or current selection. Uncovered paths keep base values; failed/skipped coverage requires explicit confirmation of that partial scope. Pending marker resolutions require an explicit checked resolution recipe. Validate complete resulting source closure before admission. Default history parent is the exact recorded base Revision (whose State must equal the capture base); never infer a parent by looking up equal StateIds. A State-only capture requires an explicitly chosen matching parent or explicit zero-parent authoring; first authoring from the initial empty repository supplies that zero-parent intent. Promotion creates a fresh ChangeId and caller-supplied immutable author metadata, stores observation provenance, and transfers/establishes authored-root custody in the normal idempotent admission transaction. It does not silently advance Selection or CaptureHead: an explicitly requested pointer change needs that resource's generation check. A CLI commit combines authored-root admission and its requested selection advance in one transaction; a stale selection leaves the prepared checkpoint, not a half-selected authored success. Advancing the history base without writing files is a recorded action, not an incomplete materialization; status compares actual observed files to the new base. A lost response retries the same receipt/ChangeId, not another revision; later separately requested authoring may reuse the immutable capture. Original capture retention and authored revision retention remain distinct.

Exact-value promotion is not the CLI's default file-selection policy. When authoring a subset of a broader recovery capture, construct a separately pinned selected candidate from the protected observed values and exact recorded base; retain honest Observation scope/partial-file construction metadata. Apply commit's deliberate new-file and subtree-deletion choices before confirmation. Only then author the exact confirmed candidate. Do not promote all privately protected bytes merely because the caller supplied a recovery reference, or rescan later filesystem bytes into an earlier preview.

**Observation provenance:** Authored revisions from filesystem observation or capture promotion must carry an Observation record in Provenance under the current codec family, even when no merge/move occurred. It records the base identity, observation scope/consistency, individual coverage or completed-scope coverage, known failed/skipped paths and explicit partial/resolution choices. Construct this metadata for the **selected candidate's actual observation/construction scope**, not by copying a broader recovery capture's path lists or adding its unselected source root as an audit input. Unrelated private captured/excluded/failed/skipped paths, local work identity and full scan details stay in the private receipt by default. Narrow prefixes/coverage to the selected scope; do not claim completed traversal where only selected entries were observed. Known gaps affecting that scope remain explicit and require partial confirmation. Extra private audit metadata needs explicit authoring-time disclosure consent; already-created RevisionIds are not rewritten on export. Capture receipt identity and detailed local audit links stay in private authority metadata by default; attaching that optional identity to canonical provenance is an explicit disclosure choice. This label is history metadata, never State identity; no label claims continuing filesystem cleanliness. The record's capture/receipt identifiers are non-owning audit identifiers and do not promise that expired recovery bytes remain available. Native export retains this provenance with the revision.

The [bounded selected-authoring reference](experiments/selective_authoring_reference.py) exercises regular-file subset construction and metadata projection using canonical objects; it is not a scanner, complete admission implementation or durability proof.

**Default retention:** ordinary private captures seven days unless explicitly changed; separately pinned unfinished work follows the resume/discard obligation below; unpinned orphaned authored revisions ninety days; accepted or explicitly pinned roots while selected/referenced, subject to deliberate retention policy and backup. These are v0 defaults, not claims of infinite durability. Quota exhaustion must reject new captures clearly, not delete older still-acknowledged captures without respecting their horizon.

**Addressing unfinished work (candidate navigation model):** Reuse local navigation, Capture, root-pin and operation-receipt metadata, not a canonical Task object or a second history graph. A stable local reference distinguishes two efforts at the same base before either has an authored Revision. Allocate its never-reused local identity when starting independent work, with a collision-checked displayed handle and optional name. Names are mutable labels; closing/renaming does not recycle identity or reattribute receipts. Starting work from authored source or the selected unauthored base creates a distinct reference, not an inferred resume of equal-base work. Exact reference syntax and presentation need workflow qualification, not new canonical kinds.

An active binding resolves the workspace's authoritative Selection and recovery observations; it does not maintain a competing current source/history head. Capture/receipt records retain their originating work identity. A late historical capture or CaptureHead from another effort is not current-work recovery merely because its base/source matches; filter by scope and disclose outdated observations.

An inactive binding resolves an exact immutable return descriptor, or an exact clean Selection if no unfinished source needs restoration. A retained local reference protects its base Selection; the until-resume obligation additionally protects unfinished captured source/pending data. Capture, first authoring and resumption do not silently replace that local identity with a checkpoint timestamp or ChangeId.

Clean work may remain named. Close an inactive clean reference explicitly to remove its navigation/base protection, not separate capture/receipt obligations. Active or operation-reserved references cannot close in isolation: navigation or workspace unregistering must first detach them, optionally in the same confirmed action. Closing unfinished inactive work requires a separate explicit discard decision; it cannot silently remove the until-resume promise. Reference closure does not erase independently retained captures. Repository-level discovery includes active, clean and preserved references from closed workspaces, with protection/availability shown. Names must distinguish saved-work versus authored-change resolution; ambiguous input refuses or requires disambiguation.

Each registered workspace has one active work binding and each work reference has at most one active workspace. Another workspace at the same immutable base has its own work identity, not a stolen binding. A resume reserves both involved work references and the destination workspace through completion or explicit incomplete-operation recovery; competing claims cannot pass merely because the reference still appears inactive. A concurrently requested copy uses a new identity with its own exact base/origins and retention; it never releases the original descriptor's obligation. Binding/navigation changes have their own never-reused generation, checked with relevant operation completion; independent capture advancement does not rebind work. Incomplete operations remain explicit.

**Preserve-and-return switching:** Before departing dirty work, durably admit and pin an immutable private descriptor containing the exact Selection target (including StateOnly/Revision), captured working source, coverage/consistency, per-path observed origins and pending typed-resolution/presentation state. Retain its record and complete base/source/pending-byte closure independently of CaptureHead or ordinary capture expiry. Preserved tracked edits and eligible new files are removed from the destination source even where the authored bases agree; switching does not transplant them. Unknown coverage cannot support an all-work-preserved claim. Show path dispositions before proceeding. Ignored/excluded paths require separate inclusion consent if preservation is needed; otherwise non-overwritten local paths remain directory-local.

Prepare and pin exact references before confirmation. Before filesystem mutation, conditionally reserve the destination/work bindings and persist intent/before-images against the prepared generations. Only verified completion atomically changes the active/inactive bindings, Selection, previous-switch navigation, handoff roots and durable receipt. Generation-check all involved work bindings and workspace Selection/materialization, not just equal target IDs; a stale completion retains protection and cannot claim success.

Resume selects the descriptor's frozen **history base** and materializes its captured source; do not select the WIP State as a replacement StateOnly base, infer ancestry from equal source, follow rewrite successors or manufacture an authored revision. A resumed new/private file keeps its observed origin relative to the descriptor's recorded base; later deliberate authoring establishes tracking in its new Selection without mutating older observations.

Previous-completed-switch navigation is a one-slot shortcut (A → B → A leaves B as previous), not a pop stack, identity or sole discovery path for older work. If the previous reference is active/reserved elsewhere or closed, report that rather than substituting a revision/capture by equality or recency. Clean references protect their selected base while retained, not every older recovery observation; expired historical targets are reported unavailable rather than retargeted.

Each unresumed descriptor protecting unfinished work has a private root pin until successful resume or explicit discard (or a separately agreed, disclosed deadline). This does not extend every historical capture's deadline. Quota failure refuses before filesystem mutation. Protect both departing work and returning source/before-images during resume. Changing Selection alone cannot release protection: guarded materialization must verify, then the generation-checked completion transaction durably hands source/record protection to the current recovery capture or another explicit root before releasing the inactive pin. Disclose the new deadline; it does not expire still-required active presentation inputs owned by Materialization. Failure, interruption or stale completion keeps both protections; no normal switch skips an unresolved Incomplete materialization. Record completed navigation only on success. Existing GC protection-generation, receipt retry and reader-lease rules apply.

**Workspace unregistering:** Normal closure first prepares an exact clean return Selection or explicitly preserves dirty observed work using the same coverage/origin rules as departure; refuse unknown coverage and unresolved materialization rather than claiming uncaptured files are safe. Its completion atomically makes that descriptor/base protection repository-owned, detaches the active binding and removes registration. Discovery and promised roots cannot depend on a join through existing workspace registrations. Removing filesystem contents is separate and explicit. Administrative recovery of an inaccessible registration must still retain existing promises and report unobserved live files as unknown; it is not a completed preserve-and-close.

**Transferring unfinished edits:** Leaving work behind is not carrying it onto another base. A checked transfer pins the original base/observations, selected edits and computed leftovers, plus destination base/current source, before preview. Construct results under the existing conditional source/merge contracts; equal source does not authorize relabeling ancestry. Retain both inputs through cancellation, conflict, stale completion or incomplete materialization. Do not remove selected work from origin custody or report a completed move until the explicitly chosen result and requested navigation/materialization outcomes complete. Later external writes are not inferred to be the selected edits. No implicit mutation of another active workspace is authorized. The user interaction and full transfer state machine remain to qualify before enabling this operation.

The independent [bounded work-lifecycle model](experiments/work_lifecycle_model.py) exercises resume protection, binding reservations, delayed capture attribution, registration closure and the durable handoff. It abstracts complete immutable closures and authority transactions; it does not implement capture selection, journal/path guards, real filesystem recovery or the full workspace state machine. The [paper walkthrough](research.md#16-local-work-addressing-and-resume-qualification--october-28-2026) records remaining interaction costs, not usability validation.

**Two materialization contracts, for usability and safety:**

- **Fresh-directory restore / new workspace** is the default for recovery and agent branching, and the only portable strongest no-clobber path. Allocate a new empty destination, record durable intent, construct files with dirfd-relative safe operations, verify them and mark ready. Never overwrite the original working directory.
- **Ordinary in-place switch** is the normal serial-task path, not atomic against arbitrary writers. Serialize **materialization operations for the same destination identity**, independently of other workspaces. Before any mutation, scan all affected tracked/untracked paths and nested obstacles; refuse dirt, coverage gaps, unknown obstructions and case collisions by default (including untracked files inside a directory slated for removal). Require explicit preservation policy or managed writer exclusion to proceed in those cases. Admit and **durably pin a before-image of every path at risk**, then persist a journal binding destination identity, selection/materialization generations, intended State, path-level pending actions, marker-presentation manifest and recovery receipt **before** changing the first path. Stage files outside conflicting names, perform path-safe guarded replacements/removals with recorded per-path outcomes, then verify from disk and conditionally finish only against the same selection/operation generation. An uncoordinated editor may race even between verification and return; `Verified` means **verified at recorded observation**, never a continuing clean guarantee. After a crash, journal replay may finish/restore only if inode/path guards still match; otherwise leave `Incomplete`, preserve before-images and require deliberate recovery in a fresh directory. No blind replay or rollback over newer third-party edits. Managed writer exclusion (or actual OS snapshot plus coordination) is needed for stronger guarantees.

OS check-then-rename does not revoke open descriptors. Use dirfd/handle-relative traversal without following untrusted symlinks, cross-device/unsupported-operation checks, flushes appropriate to the declared crash guarantee and destination identity rechecks. Materialization may use CoW/reflinks/overlay/VM snapshots, but none is mandatory. A crash leaves pinned before-images plus an explicit incomplete outcome, never a fictitious complete checkout. A capture records admitted bytes per path and explicit failed/skipped coverage; a quiesced or snapshot consistency label requires evidence of the claimed writer/FS boundary, not just two matching scans.

**Optional managed-workspace boundary (not a v0 prerequisite):** A future mounted/virtual filesystem may observe operations and use copy-on-write private overlays, stable *workspace-local* inode/handle identities and kernel cache invalidation to avoid ordinary post-hoc scans. These IDs and incidental OS metadata remain outside canonical StateId; recorded rename intent requires verified original/destination bindings, not an assumption that equal contents imply a move. `WriterQuiesced` or `FilesystemSnapshot` requires proof that **all relevant writers, including buffered/mapped I/O and outstanding handles**, were covered or stopped at the stated boundary; an intercepted write alone does not prove a coherent snapshot. Distinguish write visibility, OS-level `fsync`/`fdatasync`/directory-sync completion, protected Capture receipt and fully durable Revision/draft-root acknowledgement. A mount advertised as durable must not report successful sync when backing persistence is unimplemented (including an `ENOSYS` FUSE response the kernel treats as success). Failure or uncertain mount teardown must retain recoverable acknowledged source; invalidation of open handles/dirty pages on root switch must be qualified per platform. No FUSE, daemon, container, or virtual mount is required for ordinary AVC workspaces.

## 9. Durable storage, crash ordering, GC and backups

Local authority is **one repository-scoped SQLite database in WAL mode with synchronous=FULL** on qualified local filesystems. It owns all acknowledged immutable payload bytes as well as roots/generations, staging, protection leases, receipts and outbox. Verify effective connection settings, not just successful PRAGMA execution. SQLite owns database/WAL ordering; this is not a raw single-file-copy guarantee or a multi-host database. No external immutable object-file backend is required for the initial core.

**Logical objects versus physical segments:** BlobId still hashes the exact whole byte stream under section 3's u64 length envelope. Store large payloads in bounded segment rows, not one SQLite BLOB or a giant write transaction: SQLite limits both values and encoded rows. Segment size/placement are physical choices, not source identity. If length is unknown, stage bytes and determine length before streaming the exact hash envelope, rereading as needed. Admission verifies length, consecutive segment coverage without holes, digest, canonical references and complete closure; a sealed payload is immutable. Compression/chunking cannot substitute a hash of segment hashes for BlobId.

**Admission protocol:**

1. Establish durable staging and GC-safe protection for the **whole reused/new dependency closure before relying on it**. A previously admitted pinned root can protect reused subtrees; otherwise protect individual staged objects. Refuse or restage unavailable/reclaiming objects. An allocated row or upload reservation is not proof of resident bytes.
2. Commit bounded payload batches under staging protection. These earlier commits acknowledge **no** State/Revision/Capture root. Stream verification and closure traversal outside the final writer transaction while complete dependencies remain protected; seal verified objects and bind the admission proof to the exact staged closure. Do not hold the single writer while hashing files, traversing history, running merges or awaiting network responses.
3. In **one short FULL transaction**, resolve scoped idempotency first; reject reuse with a changed request digest. Check expected generations, authorization/policy where applicable, and verified, still-protected resident closure. Atomically transfer protection to retained roots/pins and store root, receipt and outbox. Failure changes none of those logical resources; commit is the acknowledgement boundary. A lost reply is queried/retried with the same key, not re-executed.
4. Reopen roots/receipts after interruption. Incomplete stages remain unacknowledged and recoverable only within their explicit retention; reclaim expired stages under the same GC barrier. No cross-store file-install, directory-sync-before-root or external unlink ordering is needed for object custody. Workspace materialization and exported files **still** need their separate filesystem journals/flushes.

**Reader/GC interlock:** Acquire a protected root/closure lease transactionally before dereferencing objects. A reader spanning short read transactions needs that lease; a long SQLite read snapshot can prevent checkpoint progress and grow WAL. Stop or renew before lease expiry. GC marking is advisory: serialize logical retirement against **current** roots, staging, readers and export leases, not a stale root snapshot. The initial collector snapshots protected roots under a scan lease and traces outside the writer; its short retirement transaction requires an unchanged, never-reused protection generation and an unmarked candidate. Every mutation that can change protected closure increments that generation transactionally. Lease expiry is an authority mutation, not an unversioned wall-clock filter during collection. A mismatch restarts collection, not workspace admission; this conservative barrier can starve under sustained protection churn and must be resource-qualified before optimizing it. A protected object cannot retire; a new pin must reject a retired/unavailable object. Small payload deletion can be one atomic SQL transaction. For a large object, retire its unprotected live header first, reject reuse of its physical key until bounded segment cleanup finishes, then remove the retired header. This is SQL-only reclamation, not an external-file unlink/path-reuse protocol. Traverse all **owning** Revision/State/Conflict/Provenance dependencies, capture/draft roots and explicitly pinned private evidence roots. Never mark or hydrate audit commitments as dependencies. Reclaimed pages can be reused without shrinking the database file; compaction needs separate resource qualification.

**Private evidence custody:** Verification/replay resolves IDs only from explicitly authorized input roots and their owning closure, protected under the existing staging/reader protocol before use. Optional private audit retention pins an exact input-root descriptor with its own receipt/deadline in the local authority. That descriptor enumerates the actual State/Revision/Entry and evidence dependencies needed by the operation, not merely a ProvenanceId whose inputs are non-owning; no new canonical bundle kind or permanent dependency is needed. Missing/expired evidence returns `UnavailableEvidence`; it does not invalidate an otherwise complete authored revision or authorize inferred moves. Exporting audit evidence is a separate disclosure of those exact protected roots, never an automatic consequence of source export.

**Two backup paths:**

- A completed **SQLite online backup** contains a consistent metadata **and payload** image. Read its root set, generations and manifest from the completed backup, not a separate earlier live query; incremental copying can restart under concurrent writes. Verify the closed destination, persist it under the supported filesystem contract, and reconstruct independently. Do not copy only the live main DB file while committed bytes may be in WAL. No external-object backup lease is needed for this self-contained image. Treat it as an independently retained snapshot; verify/recover selected roots before applying live expiry or GC on restore. It includes private recovery/evidence and possibly discarded sensitive versions, not merely source-publication scope; disclose that repository-wide scope before transfer. A physical DB image requires repository-wide authority; path-scoped principals receive only authorized native exports.
- A **native selected-root export** spanning short transactions must atomically select its exact immutable root/generation descriptor and establish a durable closure lease (e.g. under BEGIN IMMEDIATE) before enumeration. Root advance/expiry cannot shrink the export. Write the complete selected **owning** closure and explicitly selected metadata manifest (not private recovery/evidence roots), verify equality with that descriptor, flush the destination and only then release its lease. Native export is independent of SQLite layout and may be incremental by exact object ID.

These contracts rely on honest sync/locking and a qualified VFS/filesystem/host; they do not survive lying storage or loss of every acknowledged copy. Process-kill tests do not prove power-loss safety. Retention expiry is outside the promised horizon; earlier source loss is a correctness failure. Hashes detect corruption, not repair it. Remote receipts separately declare their replication/durability class.

**Trade-off and extension boundary:** One authority reduces trusted cross-store code, not necessarily latency or storage bytes. WAL volume, checkpoint starvation, writer contention, large-file streaming, quota/disk-full behavior, bounded reclamation and backup cost require representative tests. Later compression, CDC, bounded deltas or physical packs may preserve IDs. Introduce an external payload backend only for measured need with a qualified migration/custody protocol; do not quietly restore the hybrid via a size threshold. No mandatory Git packs, dense IDs, Raft or S3.

## 10. Native protocol, hosting and publication

The local library owns the closed SourceTransform, Merge and Observation contracts; the native service later exposes those same semantics. Initial local operations include typed GetState/GetPath/GetFileRange, ListDirectory, DiffState, ancestry/history queries (derived), conditional Apply, CreateRevision, Merge, native export and root pins. Network batches, draft handoff and target publication arrive in their separate roadmap stages, not as initial-core dependencies. Requests have negotiated format/protocol family, bounded lengths/recursion/transfer budgets and explicit complete/pending/unknown outcomes. Mutations carry a caller-scoped idempotency key, canonical request digest and expected generation/epoch; receipts persist failures whose outcome must not be repeated, successful roots and associated event IDs. Requests are authenticated and independently authorized at resource/closure scope; do not imply that a hash grants read permission.

**Full client:** holds the object closure for selected retention roots, can author/inspect/merge offline. **Partial client:** explicitly records promised missing objects, hydrates by exact ID/path witnesses or asks service to build verified source. **Thin remote client:** may query/compose without any working tree checkout. **Bulk transfer:** compressed, resumable selected-object closure/history bundles avoid one network RTT per node; sparse exact-object queries avoid shipping whole history. No native Git format requirements.

**Offline readiness:** Distinguish sparse directory materialization from partial object custody. Readiness describes exact retained roots and operations, with complete local dependency closure or explicit missing/promised requirements; it does not certify toolchain/dependency/network-service availability. A populated working directory or successful sparse fetch is not proof of independent history/merge/export capability. Protection/leases must cover the roots relied on while checking and using that result.

**Git interoperability boundary (deferred interface):** Native source/history semantics do not require a Git backend. Explicit conversion is a likely starting point, but choosing conversion alone, a synchronized bridge or a protocol-facing adapter remains open pending actual workflow and engineering evidence. None may redefine native authority. Every adapter declares its source/history subset and an explicit native-to-Git ID mapping; Git commit/object IDs never substitute for native State/Revision identities or attestations. Git has no native typed-conflict value, ordinary Git index/checkout workflows do not preserve tracked empty directories, and v0 cannot directly represent Git submodule/gitlink entries. Metadata and names may also be unrepresentable. Reject unsupported/lossy conversion by default; any user-authorized loss needs a manifest and must not be advertised as a lossless round trip. An opaque native archive carried alongside Git is archival preservation, not an ordinary Git source representation. Native verified export remains the full-fidelity custody path.

**Ephemeral agent invariant:** the worker may report safe termination **only** after a receiving authority durably acknowledges a **pinned immutable Revision/State draft root and its complete authorized closure**, with an operation receipt, retention deadline/durability class and ability to fetch/reconstruct it. Resumable uploads and retries do not turn incomplete/promised objects into an acknowledged draft. After an unknown response, query the exact idempotency receipt; do not destroy the sole surviving source until a successful durable receipt is verified. A private handoff need not create an authored Revision: protect the State/draft descriptor, exact recorded history base and pending/path-origin data necessary for the promised resume, and all of their owning dependencies. A State-only receipt without that metadata cannot promise preservation of original parent intent. Worker runtime/VM state, toolchain cache and generated binaries are not source history.

### Future hosted integration (not an initial-core object or gate)

Source/history publication never follows non-owning audit IDs or strips/rebuilds a Revision secretly. Additional construction evidence required by target policy needs separately authorized, protected input transfer; it may reveal discarded private content and requires explicit disclosure. Commitments still expose paths/fingerprints, not metadata anonymity. Full private backups and selected source publication have different disclosure scopes.

A review integration must bind observations/approval to exact revision/candidate versions and their comparison base/scope, not ChangeId alone. Evolution or equal result States do not transfer approval implicitly; any reuse policy must be explicit and preserve the original scope. Older reviewed endpoints can be unavailable under disclosed retention. Review interfaces and approval policy belong to integrations, not a mandatory native forge or new local object kind.

**Publication candidate** is a separately versioned protocol commitment, not local kind 9. Its wire identity and evidence framing must be fixed before the hosted stage ships. It is immutable and binds target identity, **monotonically increasing observed generation** (not only the observed root—avoid ABA), observed target RevisionId, ordered chosen RevisionIds, exact typed merge/transform inputs and algorithm versions, computed resulting StateId and RevisionId, and validation-policy digest/epoch. The service recomputes/verifies that the named revision/source and recipe are consistent; for an explicitly manual result it binds a checked Transform record and the service verifies their output against the submitted State. A client assertion is not a trusted proof of integration. Validation evidence is a separate, authenticated immutable attestation **over this exact candidate ID** plus input sources, build/test/toolchain versions, declared environment, status and policy identity; it cannot enter the candidate ID (no cycle). An attestation does not establish correctness outside its declared inputs/assumptions. Validation runs outside target transactions.

**Acceptance:** In one durable linearizable transaction for **that target only**, resolve the idempotency key and immutable prior receipt first, then check candidate's expected target generation/RevisionId, policy epoch/digest, authorization at the decision point, evidence freshness/trust under current policy, complete pinned source closure and required history policy. A protected linear-history target ordinarily requires its current RevisionId to be an ancestor of the submitted revision (unless an explicit non-fast-forward policy permits otherwise). Only then CAS the target root and increment its never-reused generation; atomically make the accepted Revision's complete closure target-owned retention, and commit acceptance receipt and durable outbox event together. If object custody is in a separate authority, establish its durable target-owned protection before the CAS and bind its receipt to the acceptance; a temporary upload/proposal lease is insufficient. Retain that protection while the accepted root or another promised retention obligation needs it; an unknown CAS outcome is not permission to release it. The caller may safely retry unknown outcomes with the same key+payload; a conflicting payload under the key fails, and consumers dedupe at-least-once outbox delivery by event ID. Authorization revocation can limit receipt disclosure without undoing a prior committed acceptance. On stale target/policy/evidence, retain the candidate and source as a proposal; rebuild and revalidate a **new candidate** rather than transplanting old evidence.

Default protected target: **validate before acceptance**. An explicit high-throughput policy may separate accepted and verified target roots, with deployment gated on verified. A clean text merge is never sufficient evidence of program correctness. Long-lived deployment artifacts carry the exact source RevisionId, build recipe and validation provenance; production processes need not host AVC.

**Security and multi-tenancy:** knowing a content hash does not authorize reading it. Enforce per-principal rooted object-closure and path policies **before** object fetch, existence testing, batch enumeration, diff, CAS diagnostics, proofs and cache responses; use uniform unauthorized-error behavior. A canonical unkeyed digest inherently reveals equality **to parties already holding both IDs**, so do not promise cryptographic secrecy from hash equality. Raw Merkle witnesses can expose neighbor names and hashes; serve filtered path-scoped answers without raw cross-policy sibling nodes (or explicitly authorize such disclosure). Untrusted content never implicitly executes hooks/merge programs. Authorship/signatures are authenticated attestations outside hash integrity. Ignore patterns cannot expunge secrets from retained immutable history/backup.

## 11. Adversarial invariants and decisions

| Failure/edge case | Mandatory behavior |
| --- | --- |
| Equal source from different edit orders/histories | Identical StateId under v0 codec, possibly different RevisionIds |
| Tiny edit under a million names | Update affected Merkle map path only; no unbounded whole-directory rewrite |
| Directory rename + edit, or copy from old branch | Content subtree reuse with pinned input closure and proven relocated descendant path bounds; no permanent old-revision dependency |
| Two names differ only by case on case-insensitive OS | Source retained; unsafe materialization fails without silent rename |
| Two sides rename one file differently | Coupled subtree conflict, preserve both destinations and original values |
| Criss-cross merge/previously conflicted base | Augmented ephemeral virtual ancestry; bounded algorithms either retain all representable conflict terms or return MergeTooComplex with inputs protected |
| Same nested conflict shape/values, different authors | Same conflict source value/StateId; separate provenance/RevisionIds |
| Missing sparse path proof | Reject complete StateId; retain pending draft if requested |
| Two workspace selections, watcher capture race | Independent generations, no unnecessary logical conflict |
| Editor writes during capture | Coverage and consistency class disclose gap; no point-in-time claim |
| External editor writes during restore/switch | Fresh-directory restore guarantees no overwrite; guarded in-place switching refuses known dirt and journals observed before-images, but cannot promise no races from uncontrolled writers |
| Crash/GC during staged blob publish | No acknowledged root loses protected object closure |
| Amend/rebase removed a private non-parent input | Successor source export follows owning history only; audit claims cannot pull removed bytes into public closure |
| Remote agent dies after uploading only blobs | No "saved work" claim until durable pinned draft receipt |
| Target advances after candidate was validated | Conditional acceptance fails; evidence is not silently transferred to new candidate |
| Malicious path/symlink/huge nested conflict | Fail safely; no filesystem escape, code execution, or dropped alternatives |

**Selected architectural constants (v0):** snapshot-root authority; exact State/Revision/ChangeId separation; BLAKE3-256 typed IDs; deterministic nibble radix child maps with <=4096-byte canonical leaves; byte-exact regular files/symlinks/empty dirs; source-only conflict values and separate origins; conservative merge/rebase; private bounded captures; independent per-workspace roots; SQLite-only local custody with bounded physical staging; native exchange and later hosted conditional targets; no required Git compatibility.

**Qualification before format freeze:** exact golden vectors and parser limits, conflict normalization and text-merge fixtures, filesystem fsync/name portability, and representative resource/layout comparisons. Correct or replace a failing candidate before stable user data exists; after release, changing canonical bytes requires a new format identity and explicit migration. Evidence may revise a selected implementation without reopening product requirements.

**Current implementation:** none of this native engine is implemented. Rust 0.0.1 remains a Git-command/JSON-log prototype with none of the advertised native guarantees. The research fixtures are not release qualification.


## 12. Normative v0 field order and canonical expansion rules

This section fixes the **object payload grammar** referred to in sections 3–6. Notation: byte[n] is exactly n bytes, ref(k) is u8(actual kind) plus byte[32] digest with kind validation, and str is u32le byte-length plus raw bytes. Hash envelope is defined in section 3 and is not repeated inside a payload.

    Entry =
        0x01 ref(Blob) u8(executable=0|1)      // ordinary file
      | 0x02 ref(Blob)                         // symlink target bytes
      | 0x03 ref(MapLeaf|MapBranch)           // directory
      | 0x04 ref(ConflictValue)               // unresolved source
    MaybeEntry = 0x00 | 0x01 Entry            // 0=absent; 1=present
    StatePayload = Entry                      // only Directory or a
                                              // CoupledSubtree conflict with
                                              // present directory alternatives

    MapLeafPayload =
      u32le(n)
      repeat n: u16le(suffix_nibbles), packed_nibbles(suffix), Entry

    MapBranchPayload =
      u16le(common_prefix_nibbles), packed_nibbles(prefix),
      u8(terminal_present=0|1), if 1: Entry,
      u16le(child_bitmap),
      refs(MapLeaf|MapBranch) in ascending nibble-slot order

    RevisionPayload =
      ref(State), u32le(parent_count),
      repeat parent_count: ref(Revision) in authored first-parent order,
      byte[16](ChangeId),
      str(author_bytes), str(description_bytes), i64le(unix_ns),
      u8(provenance_present=0|1), if 1: ref(Provenance)

The MapLeaf and MapBranch **actual kind tags** are distinct in their object IDs. A MapRef uses the appropriate actual tag. Every decoded map is checked against canonical leaf size, maximal shared prefixes, child-map membership, sorted key uniqueness, nibble padding and forced leaf/branch normalization; otherwise it is rejected even if its outer digest verifies. An `if 1` field following its own explicit presence flag contains **only the value bytes**, never a duplicate presence byte. An Entry at a map terminal names the exact **byte-complete** key ending at that nibble prefix; a terminal at odd total nibble depth is rejected. A map object is validated in its enclosing directory-root context, including depth parity and reconstructed name bounds; an isolated child hash cannot establish a complete State witness.

ConflictValue has exactly two direct alternatives:

    ConflictValuePayload =
      u8(region_kind=0 PathValue | 1 CoupledSubtree),
      MaybeEntry(base), MaybeEntry(alternative0), MaybeEntry(alternative1)

Sort the two alternatives strictly by their encoded MaybeEntry bytes; duplicate alternatives resolve to the one Entry rather than a conflict. A nested Conflict is **one opaque value**, never flattened or partially cancelled. Equal/base simplification is a merge-operation rule, not permission for a decoder to invent absent history.

CoupledSubtree requires every present base/alternative to be a Directory or a **strictly directory-valued nested CoupledSubtree**. Strictly directory-valued means every nested alternative is present and recursively directory-valued; an absent nested base is allowed. A non-root CoupledSubtree may directly include an absent alternative (directory deletion), but that maybe-deleted conflict cannot be embedded as a present directory alternative. At a State root all alternatives must be present at every nested level. Decode recursively, not just by the nested region byte. Binary nesting preserves original inputs but consumes the depth budget; overflow refuses a State and retains protected inputs.

**ProvenancePayload (kind 7)** contains typed history claims, not executable code or another source log:

    ref(State)(bound_result), u8(binding=1),
    u32le(input_count: 0..64), distinct id(Revision) in role order,
    u32le(occurrence_count),
    repeat sorted by (raw path components, full typed ConflictId):
      Path, id(ConflictValue), u32le(role_count), u32le(input_index)[role_count],
    u8(record_count=1|2), Record[record_count]

    id(kind) = u8(kind), byte[32](digest)      // non-owning commitment
    AuditEntry = Entry framing, with id(...) instead of owning refs
    AuditMaybeEntry = 0x00 | 0x01 AuditEntry
    Path = u32le(component_count), str(component)[component_count]
    Paths = u32le(count), Path[count]           // strictly sorted, unique

    Record = Transform | Merge | Observation

    Transform =
      0x01, id(State)(base),
      u32le(structural_count), StructuralOp[structural_count],
      u32le(edit_count), LeafEdit[edit_count]
    StructuralOp =
        0x01, Path(source), Path(destination), AuditEntry(expected_source),
              AuditMaybeEntry(expected_destination)       // Move
      | 0x02, AuditEntry(immutable_copy_value), Path(destination),
              AuditMaybeEntry(expected_destination)       // Copy
    LeafEdit = Path, AuditMaybeEntry(expected), AuditMaybeEntry(new_value)
                                                       // absent new_value = Remove

    Merge =
      0x02, u8(mode=0 History | 1 Source),
      if History: u32le(left_input_index), u32le(right_input_index),
                  u8(permit_synthetic_bases=0|1),
      if Source: id(State)(base), id(State)(left), id(State)(right),
      u16le(source_algorithm), u32le(source_version),
      u16le(text_algorithm), u32le(text_version),
      u8(left_move_evidence_present), if 1: id(Provenance),
      u8(right_move_evidence_present), if 1: id(Provenance)

    Observation =
      0x03, id(State)(base),
      u8(base_revision_present), if 1: id(Revision),
      u64le(observed_selection_generation),
      u8(consistency=0 PerFileObserved | 1 WriterQuiesced | 2 FilesystemSnapshot),
      u8(capture_receipt_present), if 1: byte[16](non-owning audit ID),
      u8(partial_confirmed=0|1),
      u8(coverage_mode=0 IndividualEntries | 1 CompletedScopes),
      Paths(scope_prefixes), Paths(covered), Paths(failed), Paths(skipped),
      u32le(resolution_count),
      repeat sorted unique by Path: Path, id(ConflictValue), AuditMaybeEntry(chosen_value)

Records are strictly ordered by tag: at most one construction record (Transform **or** Merge) and one Observation. Observation can accompany an explicit transform/merge, so recording move intent does not erase required filesystem provenance. Records describe the **same bound result**, not a sequence of commands. All presence/permission bytes are exactly 0 or 1. Paths use raw-byte component order (shorter equal-prefix component/path first), not framing lengths. Transform paths are nonempty; requests apply section 5's checked structural batch then ordered leaf phase, with exact witnesses, explicit requested overwrites and relocation bounds. Structural array order records the request, not an unspecified sequential move effect. Replaying a Transform must reproduce its bound result before it is usable as evidence. Explicit expected values are conditions, not a second source authority. A present expected_destination claims explicit replacement consent for that exact Entry commitment; consuming the claim requires checked witnesses and never grants principal authorization.

History Merge indices name its two revision inputs; complete frontier and augmented virtual reduction are derived under section 6, not stored as checkpoints. Permission for synthetic bases explicitly applies to the whole recursive reduction. Source Merge fixes exact base/left/right States, including section 7's rebase/revert formulas; it makes no ancestry claim. Current execution whitelist: source algorithm **1/version 1** (section 6); text **0/version 0** (disabled) or **1/version 1** (avc.text.lines). Positive unknown algorithm/version pairs remain structurally inspectable but cannot execute; source tag 0 and nonzero tags with version 0 are invalid. Unknown Record tags are rejected, not retained as an opaque extension. When explicitly consumed, move-evidence commitments must resolve to Transform records and must bind/replay to the selected exact base and corresponding side State before remapping; default source-only requests supply none.

At authoring/evidence verification, Observation's optional base Revision must name its base State. Canonical decoding checks the commitments' shape, not their existence or truth. Scope prefixes are nonempty as a list, sorted, unique and prefix-minimal; the root Path is allowed. IndividualEntries mode reports **individual observed Entries**. CompletedScopes mode compactly records that traversal/admission of every selected binding under the declared scope prefixes finished without known gaps; covered/failed/skipped lists must then all be empty. The observing authority must establish that completion before using the label; it is **not** an atomic whole-subtree snapshot or a continuing clean claim. This mode avoids enumerating a million paths just to describe a successful wide-repository observation. Failed/skipped paths identify unobserved bindings or traversal boundaries; they never imply absence. Coverage labels are pairwise disjoint and within scope. Failed/skipped coverage requires explicit partial confirmation. Resolution paths are unique, within scope and carry explicit choices. An absent chosen_value explicitly chooses removal of that binding, not an omitted claim; an executed root resolution must still produce a present Directory value. Marker observations without such choices remain pending, not authored Files. For newly authored selected candidates, the observing authority emits only the selected observation scope by default; broad private recovery inventories are not inherited. This is an authoring/disclosure policy, not a new canonical wire shape or an inference made by the decoder. Capture/receipt IDs and selection generations are non-owning audit data, not lookup authority or proof of continuing cleanliness. Claimed quiescence/snapshot labels require the actual observation boundary to validate them; decoding an untrusted claim does not prove it.

An owning Revision's State must equal bound_result. Binding byte 1 is the only supported mode; unknown/retired binding modes are rejected. Bound_result is Provenance's **only owning reference**. Every other ID/Entry commitment is shape-checked without fetching, traversing or requiring its target, even if that target happens to exist locally. Inputs are distinct in role order and occurrence roles are range checked. Audit IDs may outlive their input bytes; they prove neither availability nor factual correctness. Source reconstruction/retention never depends on them. Do not promise secrecy from public paths or unkeyed fingerprints.

**Execution boundary:** Decoding verifies structure/hash/closure and has no execution effects. It neither grants authorization nor proves that a Transform/Merge actually yields its bound result. An explicitly requested replay/evidence check must protect and resolve its authorized input roots, check base/revision and evidence-record bindings, use the built-in version whitelist and reproduce that exact State; a mismatch/unknown version cannot authorize moves or publication. Observation is descriptive and has no filesystem replay. Native admission additionally enforces required observation/promotion contracts; reference codec acceptance alone is not that semantic proof. The [bounded operation reference](experiments/operation_reference.py) exercises these replay/evidence and observation obligations against actual canonical records; [initial qualification limits](research.md#19-typed-operation-and-evidence-qualification--october-29-2026) and [source-move follow-through](research.md#23-recorded-move-source-merge-qualification--october-29-2026) distinguish bounded Source Merge support from unimplemented history/multiple-mapping composition and trusted rather than measured observation facts. Pending work separately owns its typed request and input/staging pins until a durable result/refusal receipt. Continued audit replayability needs a separate evidence-retention receipt, not a hidden permanent reference from the result. Do not add a plugin registry, executable recipe blob or second canonical command log.

**Canonical size limits:** component/path bounds from section 4; author ≤4096 bytes; description ≤1 MiB; entire Provenance payload ≤1 MiB; occurrence, structural/edit, path-list and resolution counts each ≤1 million, streamed and resource-limited; parent revisions ≤64; source conflict nesting depth ≤64 (count ConflictValue objects along each source traversal path, including bases and alternatives; maps and directory Entries carry the current count without resetting or incrementing it). If a complete source cannot satisfy the bound, **fail admission** with typed `MergeTooComplex` and optionally retain a pinned pending proposal; do not store an invalid deeper object by calling it opaque. All resource and overflow checks precede allocations, and all source objects are validated with cycle/closure checks before acknowledging a root. Reference parsers additionally limit open object traversals to 256 and total reference visits to 30,000 to refuse adversarial/deep graphs before host-stack exhaustion. These are explicit fixture resource budgets, not additional canonical path/history constraints or proof that a refused graph is malformed; native verifiers must qualify bounded/iterative traversal separately.

**Pinned candidate v0 vectors (revised 2026-10-27):** The [fixture manifest](experiments/codec_vectors.json) records kind, full typed ObjectID, canonical payload bytes for small objects and size plus SHA-256/preview for large objects. The [reference builder](experiments/codec_reference.py) and [independently written strict decoder/alternate radix encoder](experiments/codec_verify.py) agree on the present fixtures, backed by a minimal BLAKE3 implementation checked against the official published hash vectors. In particular, the empty MapLeaf payload is `00000000`, with ID `avc1-b3-k02-3jc2jl6s7rrrbhdwslqnijidn7z73ly43l7yzcpk37rilrouqvoa`; the corresponding empty State payload is `03 02 da45a4afd2fc63109c7692e0d425036ff3fdaf1cdaff8c89eadfe285c5d4855c` in hex, with ID `avc1-b3-k04-vmnwhh4bsvdgr3igkr7ku35zbdkwkuwugwansvrb6vo3wniyjhmq`. **Format-release gate remains open:** Python, Node and Rust now provide executable **reference** codecs, not a production native engine or implementation-independent certification. Two independent complete encoders/decoders must agree byte-for-byte and hash-for-hash on empty source, files, binary bytes, executable flag, symlinks, prefix names, leaf/branch boundaries, moves, equal states/different authors, binary/nested path/root conflicts, typed provenance variants, result binding, retired-tag rejection and negative cases. Hosted candidate identity is a separate later gate. The format must not be treated as stable before independent cross-implementation review.
